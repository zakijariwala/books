# Storage and databases

Four storage systems, four teams, four renewal dates. A SAN under the
transactional database, an NFS filer that every application mounts because it
was there, a SQL Server cluster with a licence bill nobody enjoys explaining,
and a MySQL instance that predates the current team and holds a schema no one
has drawn since 2018. Backups run to tape and to a second filer. The restore
has been tested for two of the four.

Google Cloud does not offer a single replacement for that. It offers a menu,
and the exam is almost entirely about picking correctly from it. Storage
questions are usually cost questions wearing a technical costume; database
questions are consistency and access-pattern questions wearing a product name.

## Object storage

Cloud Storage is one product with several **storage classes**: Standard,
Nearline, Coldline, and Archive. They differ on storage price, on a retrieval
charge, and on a minimum storage duration. Colder classes cost less to keep and
more to read, and they bill you for a minimum period whether or not the object
survives that long.

The question that picks a class is how often the data will be read, and the
trap is that colder is not automatically cheaper. Data read weekly from Archive
costs more than the same data left in Standard, because the retrieval charges
dominate. Any scenario that describes frequent access to "archived" data is
testing whether you noticed.

**Lifecycle policies** are the answer to "cheapest over time". You write a rule
that transitions objects to a colder class after an age, and deletes them after
another. This matters because access frequency for most data is a function of
age: logs and telemetry are read constantly for days and almost never after
that. Teach yourself the reasoning rather than a threshold. Any specific number
of days you remember came from one scenario and will not match the next.

Two features do compliance work rather than cost work. A **retention policy**
sets a minimum age before an object can be deleted, and locking the policy
makes it permanent even for administrators. **Holds** pin individual objects
until released. When a requirement says records must be immutable for seven
years, or that a legal hold must survive an administrator with full
permissions, those are the mechanisms, and versioning alone is not an answer.

Location is the other decision. A regional bucket keeps data in one region,
which is what data-residency requirements demand. Dual-region and multi-region
buckets buy availability and read locality at the cost of that constraint.
Residency wording in a scenario overrides availability wording.

## Block and file

**Persistent Disk** is network-attached block storage, and the type sets the
performance envelope. Balanced types serve most workloads. SSD types buy IOPS
for databases. The detail that catches people is that performance scales with
provisioned size on several types, so the answer to "the database is slow on
disk" can be a larger volume rather than a different one. **Hyperdisk** is the
newer line that decouples capacity from provisioned IOPS and throughput, which
is what you want when a workload needs high IOPS on a modest volume. Local SSD
is physically attached, extremely fast, and ephemeral: it does not survive the
instance, so it is scratch space and cache, never a database's only copy.

**Filestore** is managed NFS and it is the answer whenever a scenario says
applications require a shared POSIX filesystem and cannot be modified. Its
tiers trade capacity, throughput, and availability. Look for the phrase
"cannot be rewritten to use object storage", which is the exam telling you that
the elegant answer is unavailable.

The general principle underneath: if the application can be changed, object
storage is usually cheaper and scales better than a filer. If it cannot,
Filestore exists so that constraint does not block the migration.

## Picking a database

This decision carries more exam weight than any other in the chapter. Work it
as a sequence of questions rather than a list of products.

**Is it relational, and is it a migration?** Cloud SQL runs managed MySQL,
PostgreSQL, and SQL Server. It is regional, it does high availability with a
standby in a second zone, and it is the default target for lift-and-shift
relational work. Read replicas serve read scaling and can be promoted for
regional failure.

**Does it need to scale beyond one machine while staying strongly consistent?**
That is Spanner, and it is the only answer to that pair of requirements.
Horizontal scale with strong consistency across regions is the combination no
other managed relational option offers. It is expensive, so it is wrong unless
the requirement genuinely states both halves. **AlloyDB** sits between the two:
PostgreSQL-compatible, aimed at heavy transactional and mixed analytical
workloads that have outgrown Cloud SQL but do not need Spanner's global
consistency.

**Is the access pattern a keyed lookup at high volume?** Bigtable. Wide-column,
single-digit-millisecond reads, enormous write throughput, and no joins. The
canonical shape is time series: a row key of entity plus reversed timestamp,
queried by prefix. Sensor data, financial ticks, user activity streams. Bigtable
has no SQL query engine in the sense a warehouse does, and designing the row
key *is* the schema design.

**Is it a document store with mobile or web clients?** Firestore. Document
model, client SDKs, offline sync, and real-time listeners. When a scenario
mentions mobile clients that must work offline and reconcile later, that
feature set is the tell.

**Is it analytics?** BigQuery. Serverless warehouse, separates storage from
compute, scans enormous tables. It is not an operational store. It is also not
where you put data that arrives one row at a time and is read one row at a
time.

**Is it a cache?** Memorystore, managed Redis or Memcached, for session state
and hot lookups.

## Exam traps

Strong consistency plus global scale is the Spanner tell, and it is the only
one. If a question offers Spanner without stating both, it is a distractor
priced to look wasteful, because it is.

Low-latency lookup by key and timestamp is Bigtable, not BigQuery. The reverse
trap also appears: an ad-hoc analytical query over years of history is BigQuery,
not Bigtable. The split shows up constantly, and it is worth over-learning.

Streaming raw data straight into a warehouse is the expensive wrong answer when
the requirement is cheap durable capture of data whose value is unknown. That
is Cloud Storage. Ingest to a bucket, process later, load what proves useful.

Migrating SQL Server goes to Cloud SQL for SQL Server unless a licensing term,
an unsupported version, or a feature dependency forces Compute Engine. Watch
for those constraints in the scenario before assuming the managed option.

Watch for residency requirements that quietly disqualify multi-region buckets
and multi-region database configurations, however well they meet the
availability wording elsewhere in the same scenario.

## Recap

- Storage class follows access frequency, and colder is only cheaper if the
  data really is cold. Lifecycle policies automate the decline
- Retention policies and holds do compliance work that versioning does not
- Persistent Disk performance often scales with size; Hyperdisk decouples them;
  Local SSD is ephemeral
- Database choice is a sequence: relational or not, globally consistent or not,
  keyed lookup or analytical scan, operational or warehouse
- Cheap durable capture of unshaped data goes to Cloud Storage first, not into
  a database or warehouse
