# Networking and hybrid connectivity

Your datacentre has a VLAN per tier, firewalls between them, and a pair of
MPLS circuits to a colocation facility. Somebody drew it once, in Visio, and
the drawing is wrong now.

Google Cloud networking will feel familiar until it does not. Three differences
matter enough to unlearn AWS habits over.

## VPCs are global

An AWS VPC lives in one region. A Google Cloud VPC spans every region at once,
and subnets are the regional objects inside it.

A virtual machine in `europe-west2` and another in `us-central1` can sit in the
same VPC and reach each other over private addressing with no peering, no
transit gateway, and no additional charge beyond egress. Routes and firewall
rules apply across the whole network.

This collapses a class of AWS design work. When a question describes teams in
several regions needing private connectivity, the Google Cloud answer is
usually one VPC rather than several joined together.

## Firewall rules attach to tags, not to instances

AWS security groups are objects you attach to an instance. Google Cloud
firewall rules live on the network and select their targets, most often by
**network tag**.

You tag a virtual machine `web`, then write a rule allowing TCP 443 to targets
tagged `web`. Rules carry a priority, and they apply in both directions with an
implied deny on ingress and an implied allow on egress.

Service accounts also work as firewall targets, and they beat tags when you
care about who can apply them. Anyone who can edit an instance can add a tag.
Assigning a service account requires a permission on that account, so the
firewall boundary cannot be crossed by a careless edit.

## Shared VPC has no AWS equivalent

One project owns a network. Other projects run resources inside it.

The network-owning project is the **host project**. The projects running
workloads are **service projects**. A platform team keeps the subnets, routes,
and firewall rules in the host project, and application teams deploy into them
without holding network permissions.

This is the intended answer whenever separate teams need to communicate over
private addressing while staying administratively separate. Reaching for VPC
peering instead produces the non-transitive problem below.

**Peering is not transitive.** Peer A to B, and B to C, and A still cannot
reach C. Hub-and-spoke topologies built on peering leave the spokes isolated
from each other, which is either the design you wanted or the bug you shipped.
Network Connectivity Center handles the case where you need transitivity across
many networks.

## Reaching Google services privately

Three features with names close enough to confuse, all common, all examinable.

**Private Google Access** lets a virtual machine with no external IP reach
Google APIs at their public endpoints, over Google's backbone rather than the
internet. Turn it on per subnet. Use it when a workload has no external address
and needs Cloud Storage.

**Private Service Connect** gives you an endpoint inside your VPC, with an
address from your own range, pointing at a Google API or at a service published
by another VPC. Because you place the endpoint, you control where it lives.
That makes it a data-residency control as much as a connectivity one: resources
in one region consume APIs through an endpoint in that same region.

**Private Services Access** reserves a range from your VPC for Google-managed
services, then peers a Google-owned network to yours. Cloud SQL and Memorystore
use it.

That last one carries a trap. The peering shares subnet routes and nothing
more. If on-premises systems need to reach a Cloud SQL instance across
Interconnect, you must export custom routes to the peered network. Omit that
step and the database is unreachable from your datacentre while working fine
from inside the VPC.

## Connecting the datacentre

Four options, and the exam separates them on bandwidth, SLA, and how much
network engineering you own.

**Cloud VPN** runs IPsec over the public internet. HA VPN gives you an SLA and
two tunnels. Bandwidth per tunnel is limited, and latency follows the internet.
Reach for it when the requirement is encryption and modest throughput, or as a
backup path.

**Dedicated Interconnect** is a physical cross-connect into a Google
colocation facility. You order circuits, you run BGP, and you get high
bandwidth at the lowest cost per gigabit at scale.

**Partner Interconnect** puts a service provider between you and Google. It
suits sites that cannot reach a Google facility, or bandwidth requirements
below what a dedicated circuit sells in.

**Cross-Cloud Interconnect** links Google Cloud to another cloud provider.

Confirm current bandwidth tiers and SLA terms in Google's documentation before
you sit. The figures move, and an out-of-date number is worse than none.

The decision usually turns on two questions. Does the requirement state an SLA
or a bandwidth floor that the internet cannot promise? Can you physically reach
a Google facility? The first rules out plain VPN. The second chooses between
Dedicated and Partner.

> **Exam trap.** A stated requirement for an SLA rules out Cloud VPN in its
> classic single-tunnel form and rules out anything traversing the open
> internet. Look for the SLA words before comparing bandwidth.

## Load balancing

Google Cloud load balancers split on two axes: global or regional, and external
or internal.

The **global external Application Load Balancer** is the one that surprises AWS
architects. A single anycast IP address serves users worldwide, and Google's
edge routes each request to the nearest healthy backend. You do not run one
load balancer per region and stitch them together with DNS.

That property answers a family of questions. When a case study wants low
latency for a global audience from one entry point, this is the service, often
paired with Cloud CDN and with backends in several regions.

Regional load balancers handle traffic inside a region. Internal ones serve
private clients, which is what you want in front of an internal API.

Pick on four questions: does traffic come from the internet or from inside,
does it need to span regions, is it HTTP or lower in the stack, and does it
terminate TLS.

## Recap

- One VPC spans all regions. Subnets are regional. Stop reaching for peering
  out of AWS habit
- Firewall rules target network tags or service accounts, and service accounts
  resist accidental privilege
- Shared VPC lets a platform team own the network while application teams
  deploy into it. Peering stays non-transitive
- Private Google Access, Private Service Connect, and Private Services Access
  solve different problems. Learn which by their failure modes
- Interconnect choice follows the SLA requirement and physical reach, not
  bandwidth alone
