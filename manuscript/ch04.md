# Compute: virtual machines and serverless

Your estate is a few hundred VMware guests, a rack of bare-metal boxes running
a database that predates the current team, and a Kubernetes cluster somebody
stood up for the new stuff. The guests are sized by whoever asked, which means
most of them are twice the machine they need. Two of the bare-metal boxes exist
because a vendor licence is priced per physical core and audited annually.

That estate does not migrate as one thing. It splits into three, and the
exam tests whether you can perform the split: workloads that must stay virtual
machines, workloads that should have been containers years ago, and workloads
small enough that running any server for them is waste.

## Compute Engine

Machine types come in families, and the family is the decision. General purpose
covers most things and is where you start absent a reason. Compute optimised
buys higher clock speeds per core for workloads that are CPU-bound and latency
sensitive, such as game servers and single-threaded simulation. Memory
optimised buys an unusually high memory-to-core ratio, which is what in-memory
databases and large SAP deployments need. Accelerator-optimised families carry
GPUs or attach to TPUs, and chapter 8 covers when they earn their price.

Custom machine types cut across all of it: you specify vCPU and memory
independently rather than picking from a menu. When a question describes a
workload that needs a lot of memory and few cores, and the stated goal is
avoiding waste, that is the feature being probed.

**Sole-tenant nodes** put your virtual machines on a physical server that hosts
nothing else. Two things drive them, and neither is performance. The first is
a compliance requirement for physical isolation. The second, more common, is
licensing: bring-your-own-licence terms priced per physical core need visibility
of, and stability in, the cores underneath. Sole tenancy gives you node affinity
so a VM stays put and the licence stays countable.

**Live migration** has no AWS equivalent and it changes how you plan
maintenance. When Google needs to service the host underneath a running
instance, the instance moves to another host while running. No reboot, no
scheduled maintenance email, no drain-and-replace runbook. You can set the
maintenance behaviour per instance, and workloads with attached GPUs are the
notable exception that must be terminated rather than migrated.

For a cross-cloud architect this removes a chunk of familiar design work. The
AWS instinct is to build every single-instance workload for host failure
because host retirement is your problem to schedule. On Google Cloud, planned
host maintenance is not your problem. Unplanned host failure still is, which is
what managed instance groups are for.

**Spot VMs** are preemptible capacity at a steep discount, reclaimable at short
notice. They suit batch, rendering, CI, and any queue-driven work that can lose
a worker without losing the job. They do not suit anything holding state a user
is waiting on. Committed use discounts sit at the other end: you commit to
spend or to resources for one or three years in exchange for a lower rate.
Chapter 12 carries the cost detail; what matters here is that the exam pairs
"steady predictable baseline" with commitments and "interruptible batch" with
Spot, and mixing them up is a common trap.

## Managed instance groups

An instance group is a set of identical virtual machines built from an
**instance template**. The template is immutable. Changing the shape of your
fleet means creating a new template and rolling it out, not editing machines in
place, and that immutability is the whole point.

Autohealing watches an application-level health check and recreates instances
that fail it. Note *application-level*: a health check that only proves the
machine boots will happily keep a fleet of hung processes alive, and the exam
knows it.

Prefer **regional** managed instance groups over zonal ones. A regional group
spreads instances across zones in a region automatically, so losing a zone
costs you a fraction of your capacity rather than all of it. Zonal groups exist
and occasionally win, but as a default answer regional is correct and you
should need a reason to say otherwise.

Rolling updates are the reason instance groups answer so many deployment
questions. You set the new template, then control surge and unavailability
during the roll. If the new version misbehaves, you roll back by rolling
forward to the previous template. For a large fleet needing frequent updates
with a credible rollback story, this is the pattern the exam is looking for.

## Serverless

**Cloud Run** is the default for containerised request-response workloads. You
give it a container image that listens on a port; it scales from zero to many
instances and back, charges for what you use, and requires no cluster. Anything
that fits the shape of "HTTP in, response out, stateless" belongs here unless
something specific pushes it elsewhere.

The split inside Cloud Run matters. **Services** handle requests and scale on
traffic. **Jobs** run to completion and scale on work items, which is where
batch processing and scheduled tasks go. A question describing a nightly data
transformation is describing a job, not a service, and answers that wrap it in
an HTTP endpoint are wrong.

Cloud Run's concurrency model is the detail that separates it from AWS Lambda
in most architects' heads. One instance handles many concurrent requests by
default. That makes it cheaper for I/O-bound work than a
one-request-per-instance model, and it means your container has to be safe
under concurrent requests. Setting a minimum instance count is the standard
answer to cold-start latency requirements.

**Cloud Functions** now deploys on the same underlying platform as Cloud Run
and is best understood as the event-handler entry point to it: source in, small
single-purpose handler, triggered by an event from Pub/Sub, Cloud Storage, or
similar. When you already have a container, use Cloud Run. When you have twenty
lines reacting to an object landing in a bucket, a function is honest.

**App Engine** still runs, and legacy standard-environment applications on it
are fine. It rarely wins new work. If a scenario describes a greenfield
service and an answer offers App Engine, check whether Cloud Run is also on
the list; it usually is, and it usually wins.

The ceiling on all of this is request duration. Request-scoped serverless has a
timeout measured in minutes, and the exact maximum has moved more than once, so
verify it rather than memorising a number. What is durable is the shape of the
constraint: work that runs for hours, holds long-lived connections, or needs to
keep state between requests does not belong in a request-scoped service. Push
it to a Cloud Run job, an instance group, or GKE.

## Exam traps

A licensing requirement that mentions physical cores, per-socket pricing, or an
audit points at sole-tenant nodes. Nothing else on the list gives you a
physical server.

"No modification to the application" or "the vendor supports only this
operating system" rules out containers and serverless regardless of how much
better they sound. Lift and shift to Compute Engine is sometimes the correct
architecture, and the exam includes it precisely to see whether you will
over-modernise.

"Minimise operational overhead" attached to a containerised workload almost
always means Cloud Run rather than GKE. Reach for GKE when the question
supplies a reason: existing Kubernetes investment, workloads needing
node-level control, or a service mesh requirement.

Watch for stated tolerance of interruption. "Can be restarted", "batch",
"fault-tolerant workers" are the words that make Spot VMs correct, and their
absence makes Spot wrong no matter how much cheaper it is.

## Recap

- Pick the machine family from the workload's bottleneck, and custom machine
  types when the ratio is unusual
- Sole-tenant nodes answer licensing and physical-isolation requirements, not
  performance ones
- Live migration removes planned host maintenance from your design. Regional
  managed instance groups handle what it does not
- Cloud Run is the default for containerised request-response work; jobs for
  work that runs to completion, functions for small event handlers
- Long-running, stateful, or connection-holding work is disqualified from
  request-scoped serverless, whatever else the question offers
