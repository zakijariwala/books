# Containers: GKE and the fleet

Somebody stood up a Kubernetes cluster in 2021. It runs three teams' services,
it is two minor versions behind, and upgrades happen by hand on a Saturday when
the one person who understands the ingress controller is available. The etcd
backup has never been restored. Nobody wants to touch it, which is why it is
two versions behind, which is why nobody wants to touch it.

The instinct is to move that cluster to GKE and call it done. The exam wants a
harder answer: which of those services need Kubernetes at all, who owns the
nodes afterwards, and what the upgrade story looks like once it is Google's
job rather than a Saturday.

## Standard against Autopilot

In GKE Standard, Google runs the control plane and you run the nodes. You pick
machine types, size node pools, and pay for those nodes whether pods are using
them or not. In Autopilot, Google runs the nodes too. You submit pods, Google
provisions capacity, and you pay for the CPU and memory your pods *request*.

That difference is a cost decision as much as an operational one, and it cuts
both ways. Autopilot removes the bin-packing problem and the cost of idle node
headroom, which is where most self-managed clusters leak money. It also removes
your ability to over-commit, so a cluster whose nodes are genuinely well packed
can cost more under Autopilot. The honest rule is that Autopilot wins when
utilisation is poor or unpredictable and when nobody is being paid to tune it.

Autopilot's constraints are where it stops being the automatic answer. Node
customisation is not yours: no arbitrary kernel tuning, no privileged
containers, restricted host access, and DaemonSets that assume node ownership
need rethinking. Workloads that require a specific node configuration, or
tooling that installs itself as a privileged agent on every node, belong on
Standard. Check whether a question is describing a security agent or an
observability agent with node-level requirements before answering Autopilot.

## Release channels and upgrades

Enrolling a cluster in a **release channel** hands version management to
Google. Rapid gets new Kubernetes versions earliest and suits test clusters and
teams that want new features. Regular is the middle default. Stable lags
deliberately, which is what a regulated production workload wants.

Treat channel selection as an architecture decision, not an operations
preference. It sets how much validation lead time you have between a version
reaching your test estate and reaching production, and the standard design is
different channels for different environments so that lead time exists at all.

Maintenance windows say when upgrades may happen; maintenance exclusions say
when they may not. An exclusion is the mechanism behind any requirement phrased
as "no changes during the trading period" or "freeze over the holiday season".
Exclusions have maximum durations, so a scenario asking to defer upgrades
indefinitely is describing something the platform will not do.

Surge upgrade settings control the blast radius of a node-pool upgrade: how
many extra nodes may be created and how many may be unavailable at once.
Combine them with **pod disruption budgets**, which are the application's side
of the same contract. Surge settings without disruption budgets will happily
drain every replica of a service at the same time.

## Cluster topology

A **zonal** cluster has its control plane in one zone. A **regional** cluster
replicates the control plane across three zones in a region. Losing a zone
takes a zonal cluster's API server offline, which stops autoscaling, rollouts,
and self-healing even while existing pods keep serving. Regional is the default
answer for anything production.

**Private clusters** give nodes internal addresses only. The control plane gets
its own address range, reachable privately, and **authorised networks**
restrict which source ranges may reach the control plane endpoint at all. A
question requiring that nodes have no public IP addresses, or that
administrative access come only from a corporate range, is describing this
combination. Note that nodes without external addresses need Cloud NAT or
Private Google Access to pull images and reach APIs, which is the step people
forget.

Node pools group nodes of the same configuration. They are how you put GPU
nodes, memory-heavy nodes, and ordinary nodes in one cluster, with **taints**
keeping general workloads off the expensive hardware and tolerations letting
the intended pods on. When a scenario mixes machine-learning training with web
serving in one cluster, node pools plus taints is the mechanism being tested.

## Identity

Pods should not carry credentials. **Workload Identity Federation for GKE** lets
a Kubernetes service account impersonate a Google service account, so a pod
calls Google APIs with short-lived credentials and no key material anywhere in
the image, the repository, or a secret.

This is the same principle as service account impersonation in chapter 2, and
it produces the same exam pattern: the correct answer removes long-lived
credentials, and the wrong answers all move them somewhere that feels safer.
Mounting a JSON key as a Kubernetes secret is still distributing a key, as is
baking one into an image, and as is fetching one at startup.

## Fleets and multi-cluster

A **fleet** is the unit of multi-cluster management: a group of clusters
treated as one thing for policy, identity, and configuration. Once you have
more than a few clusters, or clusters in more than one environment, the
question stops being how to configure a cluster and becomes how to keep
clusters consistent.

**Config Management** applies configuration and policy from a Git repository
across the fleet, which is how you answer "ensure every cluster enforces this
control" without a human logging into each one. Policy enforcement rejects
non-compliant workloads at admission rather than reporting on them afterwards.

**Cloud Service Mesh** adds mTLS between services, fine-grained traffic
control, and per-service telemetry. It is real complexity, and the exam expects
you to justify it rather than default to it. The justifications that hold up
are mutual TLS between every service as a compliance requirement, traffic
splitting for canary releases that the application cannot do itself, and
observability across a service graph too large to reason about from logs.

The hybrid case is the one worth remembering. Clusters running in your own
datacentre, or on another cloud, can register to the same fleet and receive the
same policy and configuration. That is the answer when a migration will leave
Kubernetes on both sides of the boundary for a long time, which describes most
real migrations.

## Exam traps

A team with no Kubernetes experience is a constraint, not a footnote. Team
capability is a legitimate architectural input, and when a scenario mentions it
alongside a containerised workload, Cloud Run is usually the intended answer.
Recommending GKE to a team that cannot operate it is the wrong architecture
however well it scales.

"No credentials in the container image" means Workload Identity. Every other
option is a way of storing a key.

A requirement for strong isolation between untrusted workloads on shared nodes
points at **GKE Sandbox**, which puts a sandboxed runtime between the container
and the host kernel. Namespaces and network policy are the wrong grain of
answer for a kernel-level isolation requirement.

Watch for control-plane availability hidden inside an uptime requirement. If a
scenario needs deployments and autoscaling to survive a zone failure, a zonal
cluster fails it even though the pods keep running.

## Recap

- Standard against Autopilot is a cost and control decision. Autopilot wins on
  poor utilisation, loses where nodes need customising
- Release channels are an architecture choice: they set the validation lead
  time between environments
- Regional clusters for production, private clusters plus authorised networks
  where nodes must not be public, node pools and taints for mixed hardware
- Workload Identity replaces key material. Any answer that stores a key is
  wrong
- Fleets carry policy across many clusters, including on-prem ones; a service
  mesh needs an explicit justification
